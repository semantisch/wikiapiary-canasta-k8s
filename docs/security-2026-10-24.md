# PHP security update and availability recovery — 24 October 2026

Both WikiApiary hostnames share this deployment. Web replicas previously used
PHP 8.2.30. The rebuilt, digest-pinned application image upgrades all installed
PHP 8.2 packages to at least 8.2.35, covering CVE-2026-109618 and CVE-2026-109619.
It disables session upload progress in all SAPIs for the subsequent
CVE-2026-115560 advisory. The cache automation runtime is pinned to PHP 8.3.36.

The image retains Canasta 3.5.2, MediaWiki, SMW and the existing visual layer;
this change does not run a schema migration. Web and job-runner workloads use
the same registry image. `wikiapiary-ghcr-pull` is a separately bootstrapped
Kubernetes registry credential, never stored in this repository. Build using
`buildah bud -f image/legacy-foreground/Containerfile -t IMAGE .`, publish it,
and update production values with the immutable digest.

During verification, uncached crawler requests had exhausted PHP workers and
the database's CPU allocation. Repeated semantic property enumeration queries
scanned a table estimated at 74.8 million rows; the oldest observed SELECT had
run for 1,116 seconds. Access logs identified meta-externalagent traversing old
revisions, diffs and semantic special pages. Recovery canceled only long-running
SELECT statements, installed the crawler rejection in Varnish, and restored
Varnish grace delivery (the old hit handler explicitly passed expired objects).

MariaDB now defaults `max_statement_time` to 60 seconds to bound runaway queries.
This also applies to maintenance connections: a deliberate large maintenance
operation may explicitly use `SET SESSION max_statement_time=0` for that session.
Do not disable the production default to accommodate a crawler or web request.
The crawler response is HTTP 429 with Retry-After; ordinary readers and APIs are
not blocked by the user-agent rule. This is an operational safeguard, not an
authentication boundary, and user agents can be spoofed.

The emergency runtime changes are persisted in the image, chart and production
values. Do not roll back to the old PHP image. For an application rollback,
retain the PHP patch layer and upload-progress setting. Temporary protected
web-runtime probes are removed after verification.
